# gk-save-rate-analysis

FC온라인 공식경기(matchtype=50) 데이터로 **골키퍼를 (선수 × 시즌 × 강화단계 8~13) 단위로**
분석한다. 넥슨 Open API로 매치를 수집해 DuckDB 단일 파일에 쌓고, 선방률·GSAx·거리존별·
타입별 지표를 내서 공개용 정적 웹페이지로 뽑는다.

> ⚠️ raw 선방률은 카드 성능이 아니라 그 카드를 쓰는 **유저 실력·수비 라인·슛 난이도가 섞인 값**이다.
> 리더보드는 카드 추천이 아니다. 슛 난이도는 **GSAx**, 유저 실력은 **강화효과(유저 내)** 가 각각 보정한다.

---

## ✨ 특징

- **교란을 두 축으로 보정** — raw 선방률의 두 교란을 각각 제거한다.
  - 슛 난이도 → **GSAx**(기대선방 모델), 유저 실력 → **강화효과(within-ouid)**
- **강화단계를 퉁치지 않음** — (선수 × 시즌 × 강화단계) 단위로 각각 순위.
- **표본 투명성** — 경기수 게이트(100~50,000 직접 입력) + 모든 순위에 경기수·선방률 95% 신뢰구간(±%p) 표기.
- **사용자 편중 제외** — 같은 집계 기간·선수·시즌·강화에서 한 유저의 경기 비중이 **35% 이상**이면 최종 `out`의 리더보드·다운로드·동일선수 비교·수비 조합·순위 추이에서 제외한다. 원본 DB는 보존하며, `scripts/update.sh` 및 `collect.sh`의 자동 후처리에도 동일하게 적용된다.
- **순위 추이** — 롤링 60일 창을 3일 간격으로 소급 샘플링해, 카드가 오르는 중인지 내리는 중인지를
  **지금 걸어둔 검색·필터 안에서** 보여준다(목록의 `변동` 뱃지 + 행 펼침 라인차트).
- **선수 부가정보** — 급여·기본 OVR·키·몸무게·체형·시즌 엠블럼·선수 이미지(fc-info + 넥슨 CDN).
- **드릴다운** — 카드별 거리 구간별(초근/근/중/원)·슛 타입별(감아차기/헤더/파워샷…) 선방률.
- **인터랙티브 공개 페이지** — 검색·정렬·행 클릭 펼침이 되는 자기완결 HTML(inline CSS/JS). 외부는
  넥슨 애널리틱스·이미지 CDN·시즌 엠블럼뿐이며 자동수집 차단(robots.txt + X-Robots-Tag).
- **복원력 있는 수집** — 스노우볼 BFS + 429 적응형 감속(반토막→느린 회복) + 중단 후 재개 + 롤링 창.
- **빠른 재빌드** — 스트리밍 파싱 + DuckDB COPY. payload 는 zlib BLOB 압축(원본 대비 13%).

## 📊 지표 설명

| 지표 | 정의 | 무엇에 답하나 |
|---|---|---|
| **종합선방률** | 선방(result=1) / (선방 + 실점). PK·자책골 제외 | "얼마나 막나" (단, 유저 교란 포함) |
| **GSAx** | 실제선방 − 기대선방. 기대선방은 (슛 타입 × 거리 구간) 리그 평균 선방률로 계산 | "슛 난이도 감안하면 얼마나 잘 막나" |
| **강화효과(유저 내)** | 같은 유저·같은 카드에서 강화 1단계 상승당 평균 선방률 변화 | "강화하면 진짜 더 막나" (유저 실력 상쇄) |
| **거리 존별** | 초근(0-5m)/근(5-11m)/중(11-16.5m)/원(16.5m+) 구간별 선방률 | "가까운/먼 슛 중 뭘 잘 막나" |
| **타입별** | 감아차기·낮은슛·헤더·파워샷 등 슛 타입별 선방률 | "어떤 슛에 강/약한가" |
| **순위 변동** | 약 1주 전 같은 창의 **선방률 순위**와 현재 순위의 차 | "요즘 오르는 카드인가" |

> GSAx 순위는 볼륨 왜곡을 피하려고 **GSAx/100슛**(슛당 초과선방 × 100)으로 매긴다. 리그 전체 Σ GSAx = 0.

> **순위 변동을 읽을 때** — 순위표는 가운데가 매우 빽빽하다. 중앙값(약 50%) 부근은 ±0.5%p 안에만
> 200장 넘게 몰려 있어(상위 1% 지점은 22장), 선방률이 0.1%p만 움직여도 순위는 수백 위가 밀린다.
> 실제로 변동이 큰 카드는 표본이 적은 쪽이 아니라 오히려 **많은** 쪽이다(경기수 중앙값 1,553 vs 전체 955).
> **큰 숫자를 큰 실력 변화로 읽으면 안 된다.** 순위 등락보다 선방률 값과 ±%p를 함께 볼 것.

## 🖥 공개 페이지 (`out/index.html`)

`gksave export` 가 만드는 자기완결 HTML. 그대로 열거나 Vercel/GitHub Pages에 올리면 URL로 공유된다.
- **검색** — 이름(쉼표로 여러 명) · 팀컬러(국가·클럽·시즌 어디든 부분일치)
- **필터** — 강화단계 드랍박스 · 급여 이상/이하 · 필터 초기화(↺)
- **지표 드롭다운** — 선방률 / 근거리(박스 안) / 중거리(박스 밖) / 1대1 / 연계·컷백 / 가성비
- **정렬** — 컬럼 제목 클릭(강화·급여·OVR·선방률·GSAx/100·경기수), 다시 누르면 오름/내림 전환
- **경기수 게이트 입력** — 100~50,000 범위에서 직접 입력 (표본 적은 뽀록 상위권을 걸러 봄)
- **행마다** — 선수 이미지·시즌 엠블럼 아이콘·급여·선방률 신뢰구간(±%p)·**순위 변동 뱃지**(▲n/▼n/NEW)
- **행 클릭 → 펼침** — 액션샷 히어로 + **선방률 순위 추이 차트** + 급여·OVR·키·몸무게·체형 칩 +
  거리 구간별·슛 타입별 표. 차트의 점에 마우스를 올리면 그 시점의 등수와 **순위를 매긴 카드 수**가 뜬다.
- **동일선수 시즌 비교** 탭(선수별 총 경기수·검색) + 강화효과 요약
- **센터백 듀오** 탭 — 같은 GK 시즌·강화에서 센터백 두 카드의 조합별 선방률·
  GSAx/100·경기당 유효슛·실점·경기수·사용자 수를 비교한다. 명단에 CB 2명과
  LB/RB가 있는 경기만 포함하며, 센터백 좌우 순서는 합친다. 풀백은 저장하지만
  첫 버전의 조합 기준에는 넣지 않는다. `defense.json`은 탭을 열 때 불러온다.
  선택한 GK와 두 CB의 선수 사진·시즌 엠블럼·강화, 캐시된 급여·기본 OVR·체격도 표시한다.
  액션 사진이 없는 카드는 얼굴 사진으로 대체한다.
  급여·키와 나머지 선수 정보는 두 줄로 나눠 바로 보여준다. 현재 정렬 지표는 강조한다.
  골키퍼를 이름·시즌으로 검색하고 시즌·강화를 선택한 뒤 듀오를 비교한다.
  첫 골키퍼를 자동 선택하지 않으며, 듀오 순위는 선택한 GK 카드 안에서의 순위다.
  `scripts/collect.sh`의 기본 후처리는 새 경기의 듀오 명단·통계와 센터백 부가정보도 갱신한다.
- **지표 설명 · 사용법** 탭 — 각 지표의 정의와 순위 변동을 읽는 주의사항
- 상단에 **데이터 수집 기간**, 하단에 **NEXON Open API 출처** 명시

## 설치

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -e ".[dev]"

# API 키·설정은 .env.local 에 (커밋 안 됨). export 로 덮어쓰기도 가능.
cp .env.local.example .env.local
#   .env.local 을 열어 NEXON_API_KEY 를 발급키로 채운다
#   (GKSAVE_RATE / GKSAVE_CONCURRENCY / GKSAVE_USER_WORKERS /
#    GKSAVE_MATCH_QUEUE / GKSAVE_DATA_DIR 도 여기서 조정)
```

> 🔒 **보안**: `.env.local`·`data/`(ouid 포함)·`out/` 은 `.gitignore` 로 커밋되지 않는다.
> API 키는 **수집 시에만** 쓰이고 공개 배포물(`out/index.html`, JSON)에는 키·ouid 등
> 민감정보가 전혀 없다 → Vercel 등에 정적 배포해도 안전.

## 사용법

```bash
# 1) 실측 게이트 — 엔드포인트·선방정의·강화범위·시즌디코드 확인
gksave spike

# 2) 수집 — 닉네임 시드 → 스노우볼 BFS. 재개 가능(끊겨도 이어서).
gksave collect --seed-nicknames "닉1,닉2" --max-matches 30000
gksave collect --refresh              # 처리한 유저 다시 열어 새 경기 보충
gksave collect --days 65              # 특정 창만 (미지정 시 롤링 COLLECT_WINDOW_DAYS=65 적용)

# 3) 집계·표출
gksave build                          # raw_match 재파싱 → gk_match/shot (4만 ≈ 28초)
gksave build-defense --days 60        # 기존 파싱 경기의 수비 명단만 추가. 중단 후 재개 가능
gksave meta                           # 선수명·시즌 캐시 (최초 1회)
gksave playerinfo                     # 급여·OVR·체격·시즌엠블럼 캐시 (fc-info, 우리 GK만·1회)
gksave playerinfo --defenders         # 수비 조합의 센터백 정보도 캐시 (build-defense 이후)
gksave export --gate 50 --out out     # 리더보드 JSON/CSV + 공개 index.html
gksave export --days 60 --out out     # 최근 60일만

# 4) 조회 (콘솔)
gksave leaderboard --gate 50 --top 20             # raw 선방률 순위
gksave gsax --gate 50 --top 20                    # GSAx 순위
gksave gsax --gate 50 --exclude-shortest          # GSAx(초근 제외)
gksave card <spId> --grade 8                      # 카드 상세 (거리존별·타입별)
open out/index.html                               # 공개 페이지 열기
```

수비 조합 기능을 기존 DB에 적용할 때는 `build-defense --days 60`을 한 번 실행한 뒤
`playerinfo --defenders`로 센터백 부가정보를 캐시하고 같은 기간으로 export 한다.
`playerinfo`는 [fc-info](https://fc-info.com)에서 급여·기본 OVR·체격·시즌 엠블럼을 조회한다.
요청은 한 번에 1개씩 보내며 기본 간격은 3초다(`--delay`로 조정, 최소 1초).
이름별 검색 결과를 실행 중 재사용하고 카드 ID와 1강 기본 능력치를 검증한다.
검색에서 못 찾는 카드는 데이터센터로 재시도하지 않으며, 선수명이 없으면 `gksave meta`로 먼저 채운다.
기존 카드 캐시는 유지하고, 데이터센터 및 과거 fc-info의 누락 기록과 새 조회 기록은 구분한다.
최근 미등재 기록을 무시하고 다시 찾으려면 `playerinfo --retry-missing`을 사용한다.
특성·국가·클럽을 수집하는 `playerdetail`·`resyncbio`는 공식 데이터센터를 유지한다.
요청 제한 시 60·120·240초 이상 대기하며 `Retry-After`가 더 길면 그 시간을 따른다.
응답 읽기·연결·타임아웃 같은 통신 오류는 5·10·20초 대기 후 같은 요청을 최대 3회 재시도한다.
재시도 후에도 실패하면 수집을 중단한다. 완료된 카드 정보는 보존되어 다음 실행에서 건너뛴다.
오류 로그에는 HTTP 상태·요청 경로·원본 오류 메시지·하위 원인을 표시한다.
카드 ID·강화 단계·필수 능력치 등 응답 검증 실패에도 HTTP 상태를 보존하고, 실패 항목과 Content-Type·응답 크기·HTML 제목을 함께 표시한다.
선수 정보 진행·오류·재시도 로그 앞에는 실행 환경의 현재 시각(`[YYYY-MM-DD HH:MM:SS]`)을 붙인다.
헤더를 받은 뒤 읽기에 실패해도 상태 코드를 보존하며, 상태를 받지 못한 경우에는 미확인으로 표시한다.
이후 새 경기는 일반 `build`에서 수비 명단도 함께 저장한다.
기존 경기의 GK·슛 통계를 지우거나 API를 다시 호출하지 않는다.
`build-defense`는 시작 시 미처리 경기 수를 표시하고, 저장 완료된 배치 기준으로
약 10초마다 완료 건수·진행률·4백 명단 수·경과 시간을 출력한다. 마지막 배치는 즉시 표시한다.
재실행 시 완료한 경기를 제외한 남은 경기 수가 새 진행률의 기준이 된다.
원본은 쿼리부터 최대 1,000행씩 읽는다. 일반·전체 빌드는 파싱 후 세 집계 테이블과
완료 표시를 하나의 트랜잭션으로 저장하므로 실패하면 기존 통계를 보존한다.
페이지와 수비 조합 JSON의 생성 버전이 다르면 결과 대신 새로고침을 안내한다.

`scripts/update.sh`의 export는 전체 슛의 난이도 모델을 한 번만 계산해 GSAx와
센터백 듀오에 공유한다. 35% 편중 카드는 듀오 대상 선정에서 제외하고, 경기수·사용자 수
조건을 통과한 조합의 경기만 개별 중간 통계로 보존한다. 그 밖의 경기는 GK별 합계로
묶지만 전체 표본의 난이도 모델에는 포함한다. 임시 결과는 같은 DB 연결에서 사용하고
정상 종료·오류·중단 시 정리하며 원본 DB는 변경하지 않는다.

듀오는 GK 카드·강화 32개씩 집계하며 완료 개수·진행률·출전 경기 수·듀오 수·단계 경과와
예상 남은 시간을 출력한다. 예상 시간은 첫 묶음 완료 후 처리한 경기 수와 경과 시간으로
계산한 추정치이며, 공통 모델 준비 단계에서는 미산정으로 표시한다.
30초 주기 로그의 현재 작업 경과와 export 전체 경과는 구분된다.
같은 거리의 슛도 입력 순서에 영향받지 않도록 정렬 기준을 고정했으므로,
기존의 임의 동률 배정과 비교하면 GSAx 값·순위가 달라질 수 있다. 단순 선방률 정의는 유지한다.

조합은 export의 경기수 게이트와 사용자 5명 이상 기준을 모두 통과해야 공개되며,
화면 기본 기준은 100경기 이상이다(더 높은 export 게이트가 있으면 그 기준을 따른다).
유효슛 0개 경기도 경기수에 포함하고, PK·자책골은 지표에서 제외한다. GSAx는
리더보드와 같은 전체 표본의 슛 타입×거리 모델을 쓰며 좌표가 있는 슛만 계산한다.
API에는 교체 시점·포지션 변경 이력이 없어, 실제 동시 출전이나 조합의 인과적 효과를
확인한 통계가 아니다. 유저·전술·풀백·상대 수준의 영향도 남는다.

DuckDB 직접 조회 — 이름·시즌 붙인 뷰 제공:
```bash
duckdb -readonly data/gksave.duckdb
#   SELECT * FROM card_stats ORDER BY matches DESC LIMIT 10;      -- 카드×강화 요약
#   SELECT * FROM shot_readable WHERE player_name='마누엘 노이어' LIMIT 20;
```

## 파이프라인

```
닉네임 → /v1/id → ouid ─┐
                        ▼ /v1/user/match 스노우볼 (응답에서 ouid harvest → 큐에 추가)
                 raw_match (zlib BLOB, match_id PK dedup) ← DuckDB 단일 파일
                        ▼ 재파싱 (스트리밍 + CSV COPY)
                 gk_match + shot   ← 우리 GK(spPosition==0) ↔ 상대 shootDetail
                        │             result 1=선방 / 3=실점, PK·자책골 제외, spGrade 8~13
                        ▼ GROUP BY
                 leaderboard · gsax · grade_effect · same_player · zones/types
                        ▼
                 out/leaderboard.{json,csv} + index.html
```

> **전역 피드 `/v1/match` 는 쓰지 않는다** — 그 matchId 가 match-detail 로 안 풀린다(400, T0 실측).
> 유효 경로는 `id → user/match → match-detail` 뿐이라 시드를 ouid 기반으로 잡는다.

## 넥슨 Open API 참고

- 인증: 헤더 `x-nxopen-api-key`
- 쓰는 엔드포인트: `/v1/id`(닉→ouid) · `/v1/user/match`(유저 매치) · `/v1/match-detail`(상세) ·
  `/static/fconline/meta/{spid,seasonid}.json`(메타)
- 호출 한도: **초당 최대 500 / 일 최대 2,000만**. `GKSAVE_RATE`는 초당 발행
  상한이며 일일 사용량은 프로그램이 자동으로 차단하지 않는다.
- `GKSAVE_CONCURRENCY`는 비동기 상세 요청의 동시성 및 HTTPX의
  `max_connections`·`max_keepalive_connections` 상한에 함께 적용된다. 연결 수를
  올리면 대기 병목은 줄일 수 있지만 CPU·메모리·발열과 429 가능성도 커진다.
- 429가 발생하면 해당 요청을 재시도하면서 현재 레이트를 즉시 절반으로 낮추고,
  조용한 시간이 지나면 천천히 회복한다. 수집 종료 시 429·5xx 누적 횟수와 감속 여부를
  출력한다.
- 이론상 최고 속도는 `GKSAVE_RATE=500`이지만, 롤링 한도·다른 호출 여유를 둔 운영값은
  `450` 정도가 적당하다. `RATE=500`이면 일일 한도를 약 11시간 만에 소진한다
  (20,000,000 ÷ 500). 실제 동시성은 응답 지연에 맞춰 `RATE × 지연시간` 이상이
  필요하다. 예를 들어 지연 5.3초면 이론상 약 2,650개의 동시 요청이 필요하므로,
  `GKSAVE_CONCURRENCY=360`은 최대 약 68 req/s 수준이다.

## 배포 (Vercel 정적)

공개 페이지는 자기완결 `out/index.html`(데이터 embed)이라 그대로 정적 배포된다.

```bash
gksave export --gate 50 --out out     # out/ 갱신
git add out && git commit -m "chore: 리더보드 갱신" && git push   # → Vercel 자동 재배포
```
- `vercel.json` 이 `outputDirectory: out` 으로 잡혀 있어, 레포를 Vercel에 연결하면
  `out/` 를 정적으로 서빙한다(빌드 불필요). `out/robots.txt` + `X-Robots-Tag` 헤더로 자동수집 차단.
- `out/` 에는 키·ouid 등 민감정보가 없다(위 보안 참고). `data/`(원본, ouid 포함)는 커밋 안 됨.
- `leaderboard.json` 이 4MB+ 라 큰 푸시가 막히면: `git config http.postBuffer 524288000`.
