# 기간별 순위 추이 (검색 조건 반영)

작성: 2026-07-28 · 등급: 보통(단일 기능 · DB 스키마 변경 없음 · 배포 변경 없음)

## 배경

"기간별 순위 변경 추이를 검색 조건에 맞춰 보고 싶다"는 요구에서 출발했다. 조사 결과 세 가지가 드러났다.

**순위는 이미 클라이언트가 매긴다.** `render.py:673-678` 에서 브라우저가 필터(이름·팀컬러·강화·급여·게이트)
적용 후 정렬해 `#` 를 붙인다. 서버는 카드 배열만 준다. 따라서 서버가 "기간별 순위"를 구울 필요가 없다 —
**기간별 카드 지표만 내려주면 검색 조건 반영은 구조상 따라온다.**

**비겹침 주간 순위 변동은 대부분 노이즈다.** 같은 주의 경기를 `match_id` 해시로 무작위 반분해
노이즈 바닥을 실측했다(반분은 표본이 절반이라 노이즈가 과대평가되는 쪽이다):

| 비교 | 스피어만 | \|Δ순위\| 중앙값 |
|---|---|---|
| 같은 주 무작위 반분 (노이즈 바닥) | 0.894 / 0.897 | 6.4% / 6.7% |
| 6/29→7/06 인접 주간 | 0.858 | 8.8% |
| 7/06→7/13 인접 주간 | 0.886 | 6.4% |
| **롤링 30일 창 1주 이동** | **0.968** | — |

표본이 절반인 반분이 실제 주간 변동과 같은 수준의 등락을 낸다. 즉 주간 창 순위 등락을 그대로 그리면
사용자는 잡음을 메타 변화로 읽는다. 롤링 30일 창은 0.968 로 훨씬 안정적이라 이쪽을 채택했다.

**최근 구간은 항상 얇다.** 일자별 커버리지는 실제 플레이량이 아니라 수집 이력을 반영한다
(7/20~27 주간은 게이트 200 통과 760장, 조밀 구간 1,484장의 51%). 2026-07-27 수집 창을 1일로 줄인 뒤로는
매일 돌리지 않으면 더 얇아진다. **추이의 최신 점은 구조적으로 과소표집된다.**

## 목표

리더보드의 각 카드가 최근 한 달 새 순위가 오르는 중인지 내리는 중인지를, **현재 걸어둔 검색·필터 조건
안에서** 판단할 수 있게 한다.

## In-scope

- 롤링 30일 창을 **3일 간격**으로 소급 샘플링한 시계열 (약 11개 시점, 2026-06-28 ~ 오늘)
- 리더보드 목록에 **순위 델타 뱃지** 컬럼 (7일 전 시점 대비 `↑12` / `▼3` / `NEW`)
- 행 펼침(기존 거리존·타입 드릴다운)에 **순위 추이 라인차트** 추가
- 델타·차트 모두 **현재 필터 풀 기준**으로 클라이언트에서 재계산
- 시계열은 `index.html` 에 embed (기존 리더보드 데이터와 동일 방식)

## Out-of-scope (로드맵 후보)

- GSAx·상황별 지표의 추이 (T1 측정 결과가 여유로우면 후속으로 승격 — 아래 가정 3)
- 스냅샷 DB 테이블·이력 축적 (소급 재계산이라 불필요)
- 시점 범위·창 길이를 사용자가 UI 에서 바꾸는 기능
- 별도 `trend.json` 분리 및 그에 따른 `.gitignore` 정책 변경
- 델타 뱃지의 통계적 유의성 판정(신뢰구간 겹침 시 숨김)

## 수용 기준

1. `gksave export` 후 `out/index.html` 에 `trend` 블록이 있고, `points` 길이 ≥ 8, 각 점의 창은 `[t-30일, t)`.
2. 리더보드 각 행에 델타 뱃지가 뜬다. 7일 전 시점에 없던 카드는 `NEW`, 게이트 미달로 빠진 카드는 `-`.
3. 팀컬러 검색에 `이탈리아` 를 넣으면 델타 숫자가 **그 필터 풀 안에서 다시 계산된 값**으로 바뀐다
   (전체 풀 기준 값이 그대로 남아 있으면 실패).
4. 행을 클릭하면 순위 추이 라인차트가 그려지고, 점 개수 = `points` 길이, 결측 시점은 선이 끊긴다.
5. 차트의 마지막 점에 "수집 진행 중 — 표본이 얇을 수 있음" 표시가 있다.
6. 차트에 "지금 데이터로 소급 계산한 값" 이라는 단서가 명시된다 (아래 리스크 1).
7. `index.html` 증가분 ≤ 1.5MB, export 총 소요 증가 ≤ T1 측정치 × 시점 수 + 20%.
8. 기존 테스트(`tests/`)가 모두 통과하고, 기존 `--days` 미지정 호출 경로의 동작이 바뀌지 않는다.

## 핵심 결정과 이유

| 결정 | 이유 |
|---|---|
| 롤링 30일 창 · 3일 간격 | 비겹침 주간은 노이즈 바닥과 구분 불가(위 표). 30일 창은 스피어만 0.968 |
| 소급 재계산 (축적 아님) | 오늘 바로 11점 확보. DB 스키마·마이그레이션 불필요 → 비가역 결정 제거 |
| 시계열엔 `matches/saves/goals` 원자료만 | 클라이언트가 어떤 필터·게이트로도 순위를 다시 매길 수 있다. 서버가 순위를 구우면 필터 반영이 깨진다 |
| `index.html` embed | 배포·CSP·`.gitignore` 정책 무변경. `leaderboard.json` 은 이미 gitignore 라 별도 파일은 추적 정책 변경을 부른다 |
| 델타 기준 = 7일 전 | 3일 전은 창이 90% 겹쳐 거의 안 움직인다. 7일 이동이 실측된 최소 유의 간격 |

## 가정 장부 (거부권만 행사하면 됨)

1. **시점은 3일 간격, 최신 점 = export 의 `since` 와 동일한 창.** 주간은 5~6점뿐이라 "추이"로 읽기 빈약하다.
   되돌리기 싸다(재계산만 하면 바뀜).
2. **델타 뱃지는 현재 선택된 지표가 아니라 선방률 기준.** GSAx 추이가 out-of-scope 이므로, 지표 드롭다운을
   GSAx 로 바꾸면 뱃지는 흐리게 처리하고 "선방률 기준" 툴팁을 단다.
3. ~~**T1 에서 스냅샷 1개 비용이 20초를 넘으면 시점을 11 → 6개(주간)로 줄인다.**~~
   **해소(2026-07-28 측정): 1.49초/스냅샷 → 11개 시점 16초.** 안전판 불필요, 11개 유지.
4. 차트는 외부 라이브러리 없이 인라인 SVG 로 그린다 (CSP `script-src 'self'`, 기존 코드도 vanilla JS).
5. 시계열 키는 `"{gk_sp_id}_{grade}"` 문자열. 기존 카드 객체가 두 필드를 모두 갖고 있다.

## 남은 리스크

1. **소급 재계산은 "그때 화면"이 아니다.** 6/29 시점 값은 그 이후 수집분까지 반영한 "지금 아는 6/29" 다.
   과거일수록 나중에 더 수집돼 표본이 두껍다. 수용 기준 6 으로 UI 에 명시해 오독을 막지만, 편향 자체는 남는다.
2. **델타가 노이즈여도 수용 기준은 통과한다.** 롤링 30일 1주 이동의 \|Δ순위\| 중앙값은 2,518장 중 151위(6%)다.
   필터를 좁게 걸면 풀이 작아져 숫자도 작아지지만, 전체 풀에서는 큰 숫자가 흔하게 뜬다. MVP 는 숫자를 그대로
   보여주고, 유의성 판정은 out-of-scope 로 미룬다.
3. **최신 점 왜곡.** 수집 창을 1일로 줄인 뒤 하루라도 거르면 마지막 점이 급락한다. 표시로 완화할 뿐 못 없앤다.
4. **export 시간 미측정.** T1 이 첫 작업인 이유.

### 자체 레드팀

- *가장 약한 가정*: "소급 = 과거 재현". 실제로는 관측 시점 편향이 있다 → 수용 기준 6(UI 단서)과 리스크 1로 승격.
- *수용 기준이 못 잡는 실패*: 델타가 전부 잡음이어도 전 기준 통과 → 리스크 2로 명시하고 MVP 범위를 좁혔다.
- *그래서 바뀐 것*: 기준 5·6을 추가했고, "주간 창 순위 추이"를 조사 근거로 기각해 롤링 30일로 확정했다.

# 실행 계획

## T1. 스냅샷 1개 계산 비용 측정 — ✅ 완료 (2026-07-28)

| 항목 | 실측 | 11개 시점 환산 |

판정: 가정 3 미발동, **11개 시점 유지**. 수용 기준 7의 상한은 `16초 + 20% = 19초`.
GSAx 는 기술적으로 가능했으나(+72초) **사용자 판단으로 제외 확정** — out-of-scope 유지, 가정 2 그대로 적용.

## T2. `agg` 에 닫힌 창(`until`) 지원

- `src/gksave/agg.py:121` `_date_pred(since, *, first)` → `_date_pred(since, until, *, first)`.
  `until` 이 None 이면 기존과 완전히 동일한 SQL 을 내도록 한다.
- `grade_leaderboard` 에 `until: datetime | None = None` 추가 후 전달. **다른 집계 함수는 이번에 건드리지 않는다**
  (out-of-scope).
- **검증**: `until=None` 으로 호출한 결과가 변경 전과 동일한 장수·상위 10 순서를 내는지 비교. 기존 테스트 통과.
- **커밋**: `feat(agg): 집계에 닫힌 창(until) 지원`

## T3. `agg.rank_timeseries()` 추가

```python
def rank_timeseries(con, *, gate, window_days=30, step_days=3,
                    end: datetime, start: datetime | None = None) -> dict
```

- `end` 부터 `step_days` 씩 거슬러 올라가며 시점을 만들고, 각 시점 `t` 에 `grade_leaderboard(since=t-window_days, until=t)` 를 호출.
- 창이 `window_days` 를 못 채우는 시점(데이터 시작 2026-06-01 이전)은 버린다.
- 반환: `{"window_days", "step_days", "gate", "points": [ISO 날짜...], "cards": {"{sp}_{grade}": [[matches,saves,goals]|null, ...]}}`
- **검증**: `points` 가 오름차순이고 길이 ≥ 8. 특정 카드의 마지막 점 `matches` 가 같은 창의
  `grade_leaderboard` 값과 일치.
- **커밋**: `feat(agg): 롤링 창 순위 시계열 집계`

**✅ 완료 (2026-07-28)** — 시점 9개(7/04~7/28, 오름차순), 카드 2,883개, 소요 **12.9초**, payload **0.43MB**.
마지막 점 2,417장이 같은 창의 직접 집계와 완전 일치. 793장은 중간에 게이트 미달 시점이 있어 결측(선 끊김).
시점이 10개가 아닌 9개인 건 데이터 시작이 6/01 **15:01** 이라 7/01 시점의 창 하한(6/01 00:00)이 못 미치기 때문.

## T4. export 에 `trend` 실기
