# 수집 파이프라인 병렬화 (유저 탐색 ∥ match-detail)

작성: 2026-08-28
등급: 큼 — 수집기 핫패스 변경, 재개·dedup 불변식 유지
상태: 구현 전 계획 — 기존 코드의 트랜잭션·실패 처리·CLI 계약 확인 필요

## 1. 배경

현재 `snowball_async`는 pending 유저를 한 명씩 처리하고, 해당 유저의 신규 match-detail만 동시에 요청한다.

이 구조에서는 창(`--days`/`--since`) 안의 신규 매치가 적거나 이미 수집된 매치가 많은 유저 구간에서 detail 동시성이 충분히 활용되지 않을 수 있다.

유저 목록 탐색과 detail 수집을 분리해 여러 유저가 발견한 매치를 연속적으로 처리한다.

단, 목록 요청과 detail 요청은 같은 API 요청 예산을 공유한다. detail 요청만으로 전체 RATE를 채우는 것이 아니라, 동일 예산에서 신규 저장 처리량을 높이는 것이 목표다.

## 2. 목표와 성공 기준

동일 레이트리밋·동일 DuckDB·동일 CLI 계약 아래에서 신규 매치 저장 처리량을 높인다.

성공 기준:

1. 같은 초기 DB·입력·RATE에서 기존 구현보다 신규 저장 매치/초가 개선된다.
2. 재실행·Ctrl+C·프로세스 중단 후 raw_match 중복과 frontier 영구 유실이 없다.
3. `--max-matches`는 이번 실행에서 실제 커밋된 신규 매치 수를 기준으로 정확히 적용한다.
4. 큐·워커·진행 중 dedup 상태가 무제한 증가하지 않는다.
5. 정상 종료·max 중단·오류 중단 시 작업이 대기 상태로 남지 않는다.
6. 기존 collect/http 테스트와 신규 불변식 테스트를 통과한다.

## 5. 핵심 설계

| 결정 | 내용 |
|---|---|
| 파이프라인 | User workers → match 작업 큐 → Detail workers → 결과 큐 → Writer |
| 공유 HTTP client | 목록·detail 요청이 기존 RATE·CONCURRENCY·재시도 정책 공유 |
| 고정 워커 수 | 큐 소비 시 task를 무제한 생성하지 않음 |
| 유한 큐 | match 작업 큐와 결과 큐 모두 상한 설정 |
| DB 접근 직렬화 | 단일 이벤트 루프에서 DB 호출 사이에 await하지 않으며, 트랜잭션 중 네트워크·큐 대기 금지 |
| Writer 역할 | 매치 저장·harvest·저장 결과 확정 담당 |
| frontier 변경 | claim·완료·복구도 동일 DB 직렬화 규칙 준수 |
| 진행 중 dedup | 같은 match_id의 대기·실행·저장 작업을 공유 |
| 재개 방식 | 미완료 유저를 pending으로 남기고 다음 실행에서 재스캔 |
| 실패 유저 | 이번 실행에서는 재claim하지 않음 |
| 완료 판정 | 목록 스캔 성공 + 관련 match 작업 완료 + 재시도 필요 실패 없음 |

단일 프로세스·단일 asyncio 이벤트 루프를 전제로 한다.

`in_progress` 복구는 다른 실행이 같은 DB에서 수집 중이지 않다는 전제가 필요하다. 기존 실행 잠금이 있다면 재사용한다. 동시 실행이 가능하다면 명시적으로 차단한 뒤 복구한다.

## 6. 아키텍처

    User workers (N)
      ├─ pending 유저 claim
      ├─ user/match 페이지 탐색
      ├─ DB 저장 여부 확인
      └─ match 작업 등록 및 공유
                 │
                 ▼
    match 작업 큐 — bounded
                 │
                 ▼
    Detail workers (고정 개수)
      └─ 공유 client로 detail 요청
                 │
                 ▼
    결과 큐 — bounded
                 │
                 ▼
    Writer (1)
      ├─ raw_match 저장 + ouid harvest
      ├─ 커밋 후 신규 저장 수 증가
      ├─ 관련 유저에 성공·실패 반영
      └─ 완료 조건을 만족한 유저 done 처리

run 제어 로직이 자연 종료, max, 취소, 치명적 오류를 관리한다.

별도 범용 파이프라인 프레임워크는 만들지 않는다.

## 7. DB 접근과 트랜잭션

### 공통 규칙

- 공유 DB 연결의 접근을 직렬화한다.
- 별도 DB lock 계층은 만들지 않는다. 단일 이벤트 루프의 짧은 동기 DB 함수로 접근 순서를 보장한다.
- claim은 선정과 상태 변경을 하나의 원자적 작업으로 처리한다.
- DB 트랜잭션 중 HTTP 요청이나 `queue.put()` 등을 기다리지 않는다.
- Writer 외의 frontier 변경도 같은 직렬화 규칙을 사용한다.
- 기존 제약·인덱스·상태 필터를 확인한다.
- frontier.state가 VARCHAR라는 이유만으로 마이그레이션 불필요를 단정하지 않는다.

### 매치 저장

다음 작업은 하나의 트랜잭션으로 처리한다.

1. `INSERT ... ON CONFLICT DO NOTHING RETURNING`으로 raw_match 신규 삽입 또는 기존 행 확인
2. 해당 매치에서 필요한 ouid harvest
3. frontier에 신규 ouid 등록

불변식:

> 커밋된 신규 raw_match에는 해당 매치의 frontier 확장도 함께 반영되어 있어야 한다.

harvest는 기존 frontier 상태를 무조건 pending으로 덮어쓰지 않는다.

`stored`는 `RETURNING` 결과로 신규 삽입을 확인하고 커밋까지 성공한 경우에만 증가한다. `have_match()` 선조회만으로 신규 삽입 여부를 판정하지 않으며, 중복 결과·실패·롤백은 증가시키지 않는다.

저장·harvest는 Writer가 호출하는 짧은 트랜잭션 함수 하나에 둔다. 별도 범용 repository·상태 관리자·DB lock 추상화는 만들지 않는다.

## 8. frontier 상태머신

| state | 의미 |
|---|---|
| pending | 이후 claim 가능한 유저 |
| in_progress | 목록 스캔 중이거나 관련 match 작업의 완료를 기다리는 유저 |
| done | 이번 패스에서 정의된 목록 스캔과 관련 작업을 성공적으로 완료한 유저 |

### 시작

- 단독 실행을 확인한다.
- 이전 실행의 `in_progress`를 `pending`으로 복구한다.
- `--refresh`는 기존 계약에 따라 `done → pending`을 수행한다.

### claim

- 이번 실행의 deferred 유저를 제외한 pending을 선택한다.
- `pending → in_progress`를 원자적으로 수행한다.
- 워커가 실제로 처리할 수 있는 만큼만 claim한다.

### done 조건

다음 조건을 모두 만족해야 한다.

- 설정된 페이지·시간 범위의 목록 스캔이 성공적으로 끝남
- 해당 유저의 outstanding이 0
- 목록 또는 detail에 재시도가 필요한 실패가 없음
- 강제 중단 대상으로 남아 있지 않음

여기서 스캔 완료는 설정된 탐색 범위의 완료이며, 유저의 전체 과거 매치를 수집했다는 의미는 아니다.

### 실패 후 pending 복귀

- 실패 여부를 기록해 이후 완료 이벤트가 done으로 바꾸지 못하게 한다.
- 이미 발행된 작업은 정상 실행 중이라면 처리 완료를 기다린다.
- 관련 작업 정리 후 pending으로 복귀한다.
- 이번 실행의 `deferred_ouids`에 넣어 즉시 재claim하지 않는다.
- 다음 실행에서는 다시 탐색할 수 있다.

## 9. 진행 중 dedup과 outstanding

### 진행 중 match 작업 공유

동일 match_id가 여러 유저에게서 발견될 수 있다.

- DB에 이미 커밋된 매치는 detail 요청을 생략한다.
- 대기·실행·저장 중인 match_id는 기존 작업에 참여한다.
- 새로운 match_id만 detail 작업을 생성한다.
- 각 작업은 결과를 기다리는 ouid 집합을 유지한다.
- 동일 유저가 같은 match_id를 반복 발견해도 중복 등록하지 않는다.

개념적 상태:

    match_id → 작업 상태 + 결과를 기다리는 ouid 집합

공유 작업의 성공·실패는 모든 관련 유저에게 반영한다.

진행 중 dedup 항목은 Writer가 저장 결과를 확정할 때까지 유지한다. HTTP 응답 수신만으로 제거하지 않는다.

### outstanding 규칙

- 유저가 고유한 미완료 match 작업에 참여할 때 1 증가한다.
- 작업이 커밋·기존 저장 확인·실패 확정되면 관련 유저별로 1 감소한다.
- 실패 확정 시 감소하더라도 재시도 필요 여부를 별도로 남긴다.
- outstanding이 0이라는 이유만으로 done 처리하지 않는다.
- 빈 목록 유저도 목록 스캔 종료 시 완료 조건을 평가한다.

### 등록과 취소

- dedup 등록과 outstanding 증가를 `queue.put()` 대기 전에 수행한다.
- 상태 확인·등록 사이에 다른 작업이 끼어 중복 등록되지 않도록 한다.
- 등록 후 큐 투입 전에 취소되는 경로를 처리한다.
- 부분 등록 실패는 롤백하거나 전체 중단 복구 대상으로 처리한다.
- 복구가 어려운 중간 상태를 조용히 무시하지 않는다.

## 10. 스테이지 상세

### A — User workers

- 기본 워커 수는 8로 시작하되 실측으로 조정한다.
- 기존 `user_pages`, `limit`, since 조기 종료 동작을 유지한다.
- DB 저장 여부와 진행 중 dedup을 확인한다.
- match 작업 큐가 가득 차면 기다린다.
- 목록 요청이 실패하면 해당 유저를 재시도 필요 상태로 표시한다.

목록 스캔이 끝나도 outstanding이 남은 유저는 in_progress 상태로 유지한다.

메모리 상한을 위해 처리 중 유저 수에도 상한을 둔다. 초기 구현에서는 User worker가 해당 유저의 최종 처리까지 기다린 뒤 다음 유저를 claim하는 방식을 사용한다.

더 많은 유저를 선행 탐색하는 구조는 실측에서 필요할 때 별도 상한과 함께 추가한다.

### B — Detail workers

- 고정 개수의 워커가 match 작업 큐를 소비한다.
- 기존 공유 client로 detail을 요청한다.
- 성공 또는 실패 결과를 bounded 결과 큐로 전달한다.
- 큐를 비우며 task를 무제한 생성하지 않는다.
- 실제 HTTP 동시성은 공유 client의 세마포어가 제한한다.

### C — Writer

- 성공 결과의 raw_match 저장과 harvest를 원자적으로 처리한다.
- 커밋 후 실제 신규 저장 수를 증가시킨다.
- 실패 결과는 관련 유저에 재시도 필요 여부를 반영한다.
- 결과 확정 후 outstanding과 dedup 상태를 정리한다.
- 유저 완료 조건을 다시 평가한다.
- 기존 진행 로그와 종료 요약 계약을 유지한다.

## 11. 실패 정책

### 목록 요청 실패

- 기존 HTTP 재시도 정책을 먼저 적용한다.
- 재시도 소진 후에는 해당 유저를 done 처리하지 않는다.
- 발행된 작업을 정리한 뒤 pending으로 복귀한다.
- 이번 실행에서는 deferred 처리한다.

### detail 요청 실패

- 기존 HTTP 재시도 정책을 먼저 적용한다.
- 일시적 오류·재시도 소진은 관련 유저 전체에 재시도 필요 상태를 남긴다.
- 다음 실행에서 유저 재스캔으로 해당 매치를 다시 발견하도록 한다.
- 다른 유저나 refresh가 우연히 복구해 줄 것에 의존하지 않는다.

영구 스킵은 기존 정책과 API 의미를 확인해 명시적으로 허용한 경우에만 적용한다. 알 수 없는 오류를 영구 스킵으로 분류하지 않는다.

### 치명적 오류

다음은 전체 실행 중단 대상으로 처리한다.

- DB 저장 또는 커밋 실패
- Writer 예외
- 작업 추적 불변식 위반
- 복구 불가능한 내부 오류

워커 예외를 로그만 남기고 삼키지 않는다. run 제어 로직에 전파해 전체 작업을 종료하고 미완료 유저를 복구한다.

## 12. 정상 종료 판정

pending이 없거나 큐가 비었다는 이유만으로 종료하지 않는다.

다음 조건을 모두 만족할 때 정상 종료한다.

1. 이번 실행에서 claim 가능한 pending 유저가 없음
2. 목록 스캔 중인 유저가 없음
3. 큐 대기·HTTP 실행·결과 대기·저장 중인 match 작업이 없음
4. 유저 완료·실패 상태 반영이 모두 끝남

Writer의 harvest로 새 pending이 생기면 계속 수집한다.

deferred 유저는 이번 실행의 작업 가능 여부에서 제외한다.

종료 판정과 신규 claim·작업 등록은 일관된 상태를 기준으로 처리한다. `Queue.empty()`만으로 판정하지 않는다.

## 13. max·Ctrl+C·오류 중단

### max 적용

- 기존 CLI의 max 입력 의미를 유지한다.
- 이번 실행에서 커밋된 신규 raw_match만 센다.
- Writer가 신규 저장 직전에 한도를 확인한다.
- 중복 행은 한도를 소비하지 않는다.
- 병렬 요청이 이미 끝났더라도 한도 초과 신규 저장은 하지 않는다.
- 한도 때문에 저장하지 않은 결과는 성공으로 확정하지 않는다. 해당 작업과 관련된 모든 유저를 `pending`으로 복구하고 이번 실행의 `deferred_ouids`에 넣어, 저장되지 않은 매치가 `done` 뒤에 영구 누락되지 않게 한다.

### 강제 중단 순서

1. 신규 claim과 작업 등록을 차단한다.
2. A/B 워커에 취소를 전달하고 종료를 기다린다.
3. Writer의 활성 트랜잭션은 커밋 또는 롤백으로 정리한다.
4. 미커밋 큐·결과를 폐기한다.
5. 더 이상 상태를 변경할 워커가 없는 것을 확인한다.
6. 남은 in_progress 유저를 pending으로 복구한다.
7. 진행 중 메모리 상태와 자원을 정리하고 종료한다.

이미 정상 완료되어 done인 유저는 유지한다. 이미 커밋된 매치도 유지한다.

shutdown 이벤트만 설정하고 끝내지 않는다. 큐 put/get·HTTP·재시도 대기 중인 작업도 종료되어야 한다.

프로세스 강제 종료로 정리 코드가 실행되지 않더라도 다음 실행의 in_progress 복구로 재개한다.

## 14. 설정

| 환경변수 | 기본값 | 의미 |
|---|---:|---|
| GKSAVE_USER_WORKERS | 8 | 동시에 처리 중인 유저 수 |
| GKSAVE_MATCH_QUEUE | 2000 | 대기 match 작업 큐 상한 |
| GKSAVE_RATE | 기존 | 목록·detail이 공유하는 요청 속도 제한 |
| GKSAVE_CONCURRENCY | 기존 | 공유 client의 전체 HTTP 동시 요청 상한 |

- Detail worker 수는 기존 concurrency 설정에서 도출한다.
- 결과 큐 크기도 detail worker 수에서 도출하며 초기에는 별도 env를 추가하지 않는다.
- 새 워커·큐 설정은 양의 정수만 허용한다.
- 기존 RATE·CONCURRENCY의 특수값 계약은 확인 후 유지한다.
- CLI 플래그는 실제 필요가 없으면 추가하지 않는다.
- concurrency=1 경로는 기존 호출 계약을 확인하고 불필요한 이중 구현을 피한다.

## 15. 관측과 성능 검증

기존 로그를 유지하고 다음을 구분해 관측한다.

- 목록 요청 수
- detail 요청 수
- 실제 신규 저장 수
- 이미 저장된 매치 생략 수
- 진행 중 중복 요청 병합 수
- 실패·deferred 유저 수
- match 큐·결과 큐 상태
- 기존 429·5xx 카운트

성능 비교 조건:

- 동일 초기 DB 복사본
- 동일 seed·시간 범위·페이지 제한
- 동일 RATE·CONCURRENCY
- 동일 실행 한도
- 가능한 한 유사한 입력과 외부 API 조건

주요 지표는 신규 저장 매치/초다. 전체 요청/초만 증가하거나 중복 요청이 늘어난 결과를 개선으로 간주하지 않는다.

신규 매치가 부족하거나 API·DB가 병목인 경우 detail idle이 생길 수 있음을 인정한다.

### 구현 후 1차 실측 (2026-08-28)

- 원본 DB의 copy-on-write 복제본, 최근 1일, 신규 500매치
- `GKSAVE_RATE=15`, `GKSAVE_CONCURRENCY=18`, User workers 8
- 36.85초, 13.6 신규 매치/초, 429 0회, 5xx 0회
- 기존 기록 8.9매치/초 대비 약 52% 높지만 입력 DB가 동일한 과거/신규 A/B는 아니므로 참고값으로만 사용한다.

## 16. 테스트 계획

외부 API 없이 fake transport와 임시 DB로 검증한다. 실행 순서 제어에는 이벤트·배리어를 사용하고, 불필요한 시간 기반 sleep assertion은 피한다.

1. claim 복구
   - 남아 있는 in_progress가 실행 시작 시 pending으로 복구됨

2. 병렬 유저 탐색
   - 한 유저의 detail 완료 전에 다른 유저의 목록 요청이 진행됨

3. 진행 중 dedup
   - 두 유저가 같은 매치를 발견해도 detail 요청 1회, raw_match 1행
   - 두 유저 모두 저장 결과가 확정될 때까지 done이 아님

4. 반복 발견
   - 같은 유저가 같은 match_id를 반복 발견해도 outstanding 누수 없음

5. 빈 목록
   - 목록 스캔 성공 후 작업이 없으면 done으로 전이

6. detail 실패
   - 재시도 소진 시 관련 유저가 pending으로 남음
   - 다음 실행에서 재수집 가능

7. 목록 실패
   - 일부 작업 발행 후 목록 실패해도 done으로 바뀌지 않음
   - 같은 실행에서 무한 재claim하지 않음

8. 자연 종료
   - pending이 없어도 진행 중 detail의 harvest 결과를 계속 탐색
   - 모든 작업 완료 후 정상 종료

9. max
   - 중복·신규 결과가 섞여도 신규 저장 수가 정확히 제한됨
   - 한도 때문에 저장하지 않은 결과의 관련 유저가 done이 아닌 pending·deferred로 남음
   - 미완료 유저는 다음 실행에서 복구됨

10. 백프레셔
    - 두 큐의 크기가 작아도 정상 진행
    - 큐 full 상태의 max·취소도 제한 시간 안에 종료

11. Writer 오류
    - 전체 작업이 종료되고 생산자가 큐 대기에 남지 않음

12. 저장·harvest 원자성
    - 중간 오류 발생 시 둘 다 롤백되거나 일관된 상태로 커밋됨

13. 취소·재개
    - 작업 등록 직후, 큐 대기, HTTP 실행, 저장 전후 중단을 검증
    - 재실행 후 매치·frontier 유실 없음

14. 기존 회귀
   - since/days/refresh/seed/max 계약 유지
   - 기존 429 대응·즉시 로그·종료 요약 유지
   - pending/done/in_progress 상태 수와 전체 유저 수가 로그·status에서 정확함
   - concurrency=1 경로 유지
